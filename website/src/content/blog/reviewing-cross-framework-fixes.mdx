A small fix is not always a small review. In a cross-framework component library, a one-line change can sit at the
intersection of a state machine, a presence utility, framework rendering semantics, and user-provided props.

AI coding tools make it easier to propose these changes, but they do not change what makes a patch trustworthy. You
still need to trace the behavior, inspect every implementation, and protect the result with tests.

Here is a practical way to do that.

## Start with the invariant

Before looking at the proposed expression, write down the behavior the component must preserve.

Consider a tour backdrop. It should be visible only when:

- the tour is open, and
- the current step enables a backdrop.

That gives us a simple truth table:

| Tour open | Step backdrop | Backdrop visible |
| --------- | ------------- | ---------------- |
| No        | Yes           | No               |
| No        | No            | No               |
| Yes       | No            | No               |
| Yes       | Yes           | Yes              |

This table is more useful than starting with the diff. It gives you something independent to test the implementation
against.

## Follow every source of state

Ark UI composes behavior from multiple layers. A component might merge props from Zag, Presence, and the consumer:

```tsx
const mergedProps = mergeProps(machine.getBackdropProps(), presence.getPresenceProps(), props)
```

Each layer has a reason to contribute values:

- Zag describes the component's current machine state.
- Presence keeps an element mounted long enough to animate in or out.
- Consumer props add attributes and event handlers from the application.

Do not assume that the last visible line in the component owns all of that behavior. Read the values returned by each
layer and identify which one should be authoritative for every state.

## Check prop precedence

The order of a spread and an explicit prop matters:

```tsx
<ark.div {...mergedProps} hidden={localHidden} />
```

Here, `localHidden` replaces the `hidden` value in `mergedProps`. If Zag or Presence returns `hidden: true`, the
component silently discards it.

That can remain unnoticed while two values happen to agree. A dependency update may change when a step is cleared or how
long an element stays mounted, exposing the conflict without introducing it.

The important review question is not only, "Does the new expression fix this reproduction?" Ask, "Which layer owns this
prop, and are we preserving all valid reasons for it to be true?"

## Inspect every framework implementation

Ark UI supports React, Solid, Vue, and Svelte. Similar-looking component files do not guarantee identical behavior.

React and Solid use JSX, Svelte has its own spread and attribute semantics, and Vue often expresses visibility through
template directives. Compare the complete rendered element in every framework—not just imports or setup code.

For each implementation, check:

1. Which props are merged?
2. In what order are they applied?
3. Is a merged prop overwritten afterward?
4. Is the element hidden, conditionally rendered, or unmounted?
5. Does the framework react when the underlying state changes?

This pass frequently finds one of two problems: a PR changes fewer frameworks than the bug affects, or it changes a
framework that already handles the state correctly.

## Separate the trigger from the defect

A regression often appears after a dependency update, but that does not automatically make the dependency wrong.

Suppose a state machine used to clear the current step on dismissal and now retains it during the closed state. That
change may expose a component that accidentally relied on `step` becoming `undefined`. The dependency change is the
trigger; overwriting the authoritative closed-state prop is the integration defect.

Before moving a fix upstream, ask:

- Is the old behavior part of the dependency's documented contract?
- Does the new behavior support exit animations or state continuity?
- Does the dependency already expose the correct state through its props or API?
- Can the integration express its invariant without relying on incidental cleanup timing?

This distinction prevents a local workaround from becoming an upstream regression.

## Test behavior, not the implementation

A regression test should recreate the sequence a person experiences:

1. Start a tour on a step with a backdrop.
2. Confirm that the backdrop is visible.
3. Dismiss the tour.
4. Confirm that the backdrop is hidden, even when the default render strategy keeps it mounted.
5. Start a step with `backdrop: false` and confirm that the backdrop stays hidden.

Avoid a test that only asserts the exact expression used by the patch. The behavior test will survive a refactor from
prop merging to conditional rendering, while still catching the original regression.

When equivalent code changes in multiple framework packages, add coverage for each changed implementation. Shared
state-machine tests cannot prove that React, Solid, Vue, and Svelte apply the resulting props correctly.

## Review AI-generated changes the same way

An AI-generated pull request can include a detailed explanation, precise version references, and a convincing fix. Those
are useful starting points, not evidence by themselves.

Verify the claims against the repository:

- Read the installed dependency code or its documented API.
- Search for equivalent implementations across frameworks.
- Reproduce the state transition.
- Run the relevant tests.
- Ask for missing regression coverage.

The attribution should not count for or against the contributor. A human-written patch can overlook a framework, and an
AI-generated patch can be correct. The same standard applies to both: the reasoning must match the code, and the tests
must demonstrate the behavior.

## A repeatable review checklist

When a cross-framework fix looks deceptively small, use this checklist:

- State the intended behavior as an invariant.
- Build a truth table for the relevant states.
- Trace props through the state machine, utilities, and consumer API.
- Verify spread and explicit-prop precedence.
- Compare every supported framework implementation.
- Separate the change that exposed the bug from the code that owns the defect.
- Add behavioral regression tests for every changed implementation.
- Treat generated explanations as hypotheses until the repository confirms them.

Good review is less about distrusting a tool or contributor and more about making hidden assumptions visible. Once the
invariant, ownership, and framework differences are clear, even a subtle one-line bug becomes much easier to evaluate.
